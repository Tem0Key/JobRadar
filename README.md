# JobRadar

Персональный агрегатор вакансий с CLI и локальной веб-панелью на Python 3.12+.
MVP собирает опубликованные вакансии
с публичных Greenhouse и Lever boards, сохраняет их в SQLite и выполняет объяснимый поиск.
Сбор не зависит от поискового профиля: сохраняются **все** вакансии настроенных компаний.
Docker и ключи доступа для этих GET-запросов не нужны. Локальный веб-сервер встроен.

Разработка: [CONTRIBUTING.md](CONTRIBUTING.md). Подготовка репозитория и команды
первого push: [публикация в GitHub](docs/publishing.md).

## Веб-управление

На Windows запустите **`Start-JobRadar.cmd` двойным щелчком**. Откроется локальная
панель по адресу **http://127.0.0.1:8765**. Окно сервера должно оставаться открытым;
для остановки нажмите `Ctrl+C` в этом окне.

Запуск из PowerShell:

```powershell
# Перейдите в каталог, в который скачан или клонирован проект:
cd "C:\Projects\JobRadar"
.\.venv\Scripts\python.exe -m jobradar serve --open
```

После получения обновлённого проекта установите зависимости в существующее окружение:

```powershell
.\.venv\Scripts\python.exe -m pip install -e ".[dev]" -c requirements-lock.txt
```

Linux/macOS: `.venv/bin/python -m jobradar serve --open`. Ключ `--open` открывает
браузер после готовности сервера; без него перейдите по адресу вручную. Другой порт:
`jobradar serve --port 8766`. Глобальные параметры БД/конфигурации работают и с `serve`.

В панели доступны:

- Вакансии: текстовый поиск и профили, фильтры, постраничный список, полное описание,
  причины совпадения и оценка географии, ссылка на оригинал.
- Запуск сбора по всем источникам либо одной платформе; состояние и результаты
  видны без блокировки интерфейса. История результатов хранится в SQLite.
- Экспорт **всех** результатов выбранного поиска в CSV или JSON. CSV в браузере
  содержит UTF-8 BOM для Excel.
- Компании: добавление реальных board identifiers, выбор Greenhouse/Lever и региона,
  включение/выключение источников.
- Поисковые профили: ключевые слова, исключения, фильтры и географические правила.
- Статистика и история запусков с ошибками по каждой компании.

Изменения применяются кнопкой сохранения. При использовании example-файлов панель
создаёт `config/sources.yaml` и `config/profiles.yaml`; примеры остаются целыми.
Следующий запуск с настройками по умолчанию, включая CLI, автоматически выберет
существующие личные файлы. Явно указанные пути CLI/окружения имеют приоритет; для
них используется выбранный файл (example-файл в веб-панели служит шаблоном для
личного соседнего YAML). YAML-комментарии в сохраняемом личном файле заменяются
стандартизованным представлением; сами настройки сохраняются полностью.
Если ваш старый `.env` явно указывает на `*.example.yaml`, удалите эти два
переопределения либо поменяйте их на личные файлы, чтобы CLI использовал изменения
из панели. Новая `.env.example` выбирает файлы автоматически.

Сервер слушает только `127.0.0.1`, работает одним процессом и предназначен для
личного использования на этом компьютере. Страница и ресурсы не зависят от CDN.
Не запускайте параллельно сбор из CLI/cron: блокировка повторного запуска действует
внутри веб-процесса. При обычной остановке сервер дожидается текущего сбора; при
принудительном завершении незавершённый сбор нужно запустить заново. Оперативный
индикатор сбрасывается после перезапуска, сохранённая история остаётся в БД.

## Быстрый запуск

Windows PowerShell, из каталога проекта:

```powershell
python --version
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]" -c requirements-lock.txt
.\.venv\Scripts\python.exe -m jobradar collect
.\.venv\Scripts\python.exe -m jobradar list
.\.venv\Scripts\python.exe -m jobradar search --query "firewall"
.\.venv\Scripts\python.exe -m jobradar search --profile "Network Security" --explain
.\.venv\Scripts\python.exe -m jobradar export --format csv --output exports/jobs.csv
```

Linux/macOS:

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]' -c requirements-lock.txt
.venv/bin/python -m jobradar collect
.venv/bin/python -m jobradar search --profile 'Network Engineering' --explain
```

После активации окружения (`.venv\Scripts\Activate.ps1` или `source .venv/bin/activate`)
можно использовать короткую команду `jobradar`. Активация необязательна. Для установки
только приложения используйте `-e .` вместо `-e ".[dev]"`.
`requirements-lock.txt` фиксирует проверенные версии зависимостей; `pyproject.toml`
описывает допустимые диапазоны для последующего обновления.

По умолчанию читаются личные `config/sources.yaml` и `config/profiles.yaml`, если
они существуют; иначе `config/sources.example.yaml` и `config/profiles.example.yaml`.
SQLite создаётся автоматически в `data/jobradar.db`. Относительные пути отсчитываются
от рабочего каталога: запускайте команды из корня проекта.

## Настройка компаний и профилей

Сделайте личные копии конфигурации:

```powershell
Copy-Item config/sources.example.yaml config/sources.yaml
Copy-Item config/profiles.example.yaml config/profiles.yaml
Copy-Item .env.example .env
```

В `.env` укажите:

```dotenv
JOBRADAR_DATABASE_URL=sqlite:///data/jobradar.db
JOBRADAR_SOURCES_FILE=config/sources.yaml
JOBRADAR_PROFILES_FILE=config/profiles.yaml
```

Приоритет настроек: глобальные CLI-параметры → переменные окружения → `.env` → значения
по умолчанию. Неизвестные поля YAML и повторяющиеся boards/имена профилей отклоняются,
чтобы опечатки не меняли поведение незаметно.

Публичные идентификаторы нельзя получать из одного только названия компании.
Возьмите ссылку с официальной страницы Careers работодателя:

- Greenhouse: `https://boards.greenhouse.io/{board_token}` или
  `https://job-boards.greenhouse.io/{board_token}` → `identifier: board_token`.
- Lever: `https://jobs.lever.co/{site}` → `identifier: site`, `region: global`.
- Lever EU: `https://jobs.eu.lever.co/{site}` → `identifier: site`, `region: eu`.

Greenhouse также встречается на собственных доменах работодателя; тогда найдите
публичную Greenhouse-ссылку на его Careers-странице. Не подбирайте токены перебором.

Пример действительных идентификаторов:

```yaml
sources:
  - name: Cloudflare
    source: greenhouse
    identifier: cloudflare
    enabled: true
  - name: Torq
    source: greenhouse
    identifier: torq
    enabled: true
  - name: Canary Technologies
    source: lever
    identifier: canarytechnologies
    region: global
    enabled: true
  - name: Atmosera
    source: lever
    identifier: atmosera
    region: global
    enabled: true
```

Пример выше — структура записей; полная конфигурация HTTP находится в
`config/sources.example.yaml`. Публичные boards проверены 14 октября 2026 года:
Canary Technologies — 31 вакансия, Atmosera — 14. Это все опубликованные роли этих
компаний; соответствие профессии и географии определяется профилем отдельно.
Torq — 25 вакансий, включая опубликованную SOC Solutions Architect с локацией
Costa Rica. Это повод прочитать условия конкретной роли, а не подтверждение
профессионального соответствия или права на работу.
`identifier: lever` означает страницу самой компании Lever, а не поиск по платформе:
она вернула корректный пустой список и теперь выключена в примере. Пустой результат
отличается от ошибки сети; в панели он поясняется отдельно. Количество вакансий
и идентификаторы могут измениться. Официальный `leverdemo` включён в пример
отдельной **выключенной** записью: это демонстрационные объявления, а не реальные
вакансии для отклика. Непустой demo board проверяется отдельным интеграционным тестом.

Пример профиля:

```yaml
profiles:
  - name: My Network Search
    keywords: [firewall, network engineer, VPN, сетевой инженер]
    title_keywords: [network engineer, network security, firewall, сетевой инженер]
    description_keywords: []
    exclude_keywords: []
    exclude_title_keywords: [sales, presales, software, recruiter]
    companies: []
    locations: []
    remote_types: [remote, hybrid, onsite, unknown]
    seniorities: []
    languages: []
    include_unknown: true
    geography:
      target_location: Costa Rica
      allowed_location_terms: [Costa Rica, Коста-Рика]
      worldwide_terms: [worldwide, work from anywhere]
      allowed_remote_region_terms: [LATAM, Latin America]
      blocked_location_terms: [US, United States, Europe, US only, Europe only]
      hard_exclusion_phrases: [must reside in the United States]
```

Готовые профили **Network Security**, **Network Engineering**, **Security Operations**
содержат английские и русские названия ролей. Общий **Мой поиск** объединяет целевые
должности и выбран при открытии панели через `default_profile: Мой поиск`.
В нём оставлены Network/Firewall/NDR/SOC и эксплуатация ИБ; IAM, Product/Application
Security и исследовательские роли исключаются по названию. Упоминание этих направлений
в описании подходящей сетевой вакансии не мешает совпадению. Общие названия вроде
`Security Engineer` без уточнения специализации требуют отдельного поиска в «Все вакансии».
Роль должна совпасть в названии: одно упоминание firewall/Palo Alto/SOC 2 в тексте
продавца или разработчика не достаточно. Исключения по названию убирают продажи,
presales, разработку ПО и другие явно нерелевантные роли. «Все вакансии» по-прежнему
доступны в списке профилей; CLI без `--profile` также показывает весь инвентарь.
Выбор стартового профиля меняется флажком в редакторе профилей. Список компаний и
предпочтения не встроены в адаптеры.

Правила фильтрации:

- Непустые группы объединяются AND; значения внутри каждой группы — OR.
  `keywords` ищет в названии и описании; `title_keywords` и `description_keywords`
  ограничивают соответствующее поле. Пустая группа не ограничивает результат.
- Ключевые слова учитывают Unicode-границы слов: `SOC` не совпадает с `social`,
  `ИБ` — со словом `спасибо`. Формы слов и синонимы добавляются явно.
- `companies`, `seniorities`, `languages`, `remote_types` сравниваются без учёта
  регистра с целым значением; `locations` ищет подстроку исходной локации.
- `exclude_keywords` исключает слова в названии/описании; `exclude_title_keywords`
  исключает только название. Например, сотрудничество с sales в описании вакансии
  Network Security Engineer не делает её продажами. Исключения имеют приоритет.
- `--query` — буквальная фраза без учёта регистра в названии, описании, компании
  и локации. Вместе с `--profile` требуется совпадение обоих условий.
- Неизвестное поле активного фильтра сохраняется с `needs_review`, если
  `include_unknown: true`; значение `false` исключает неопределённые результаты.

### География и доступность из Коста-Рики

Оценка географии возвращается отдельно от совпавших слов:

| Значение | Что означает |
| --- | --- |
| `allowed` | Найдено явное разрешение по настроенным правилам: например, Remote LATAM или офис в Costa Rica. |
| `excluded` | Найдено явное противоречие: обязательная другая география, запрещённая фраза или офис/гибрид вне целевой страны. |
| `needs_review` | Недостаточно сведений, неизвестное поле или неоднозначные условия. |

`remote` само по себе не означает worldwide. Общие упоминания клиентов, команд,
офисов или льгот по всему миру не подтверждают право работать из Коста-Рики.
Если Greenhouse пишет только `Hybrid`, дополнительно учитываются опубликованные
`offices` и `Job Posting Location`: гибридная работа в Сингапуре или Остине исключается.
Исходное поле `location` и raw data сохраняются целиком. В карточке показываются
дополнительные города; офис компании сам по себе не ограничивает worldwide-remote.
Противоречащие ограничения имеют приоритет. Профиль исключает `excluded`, но
показывает `needs_review` по умолчанию. `list` и поиск без профиля показывают
инвентарь независимо от географии, включая неподходящие вакансии.

Это прозрачные эвристики, а не юридическая проверка права на работу: `allowed`
означает соответствие найденному тексту и YAML-правилам. Проверьте оригинал до
отклика. Нераспознанные ограничения и необычные формулировки могут потребовать
новых правил. Язык не определяется предположением по ASCII: если источник не
предоставил поле, сохраняется `null`.

## CLI

Далее `jobradar` означает установленную команду из активного окружения; эквивалент —
`.venv\Scripts\python.exe -m jobradar` в PowerShell.

```text
jobradar collect
jobradar collect --source greenhouse
jobradar collect --source lever
jobradar list --limit 20
jobradar list --company Cloudflare --source greenhouse --status all --json
jobradar search --query "firewall" --explain
jobradar search --profile "Network Security" --json
jobradar search --profile "Network Engineering" --query "VPN"
jobradar stats
jobradar stats --duplicates
jobradar export --format csv --profile "Network Security" --output exports/security.csv
jobradar export --format json --status all --output exports/all.json
jobradar --database-url sqlite:///data/other.db --sources-file config/sources.yaml collect
```

Глобальные параметры указываются **перед** командой. `--status` принимает `active`,
`inactive`, `unknown`, `all`; по умолчанию `active`. `list/search --limit` ограничивает
только вывод, экспорт выгружает **все** выбранные записи. `--json` содержит полные
описания, исходные данные и объяснения; `--explain` выводит причины и оригинальные ссылки.

Экспорт без `--output` пишет данные в stdout. JSON сохраняет `null`, полное описание
и объект `raw_data`. CSV хранит вложенные поля как JSON и неизвестные значения как
пустую ячейку. CSV защищает строки с префиксами формул (`=`, `+`, `-`, `@`), добавляя
апостроф; для побитово неизменённых строк используйте JSON. Файл через `--output`
заменяется атомарно после успешного формирования.

Коды завершения `collect`: `0` — все выбранные boards успешно прочитаны (либо ни
один не включён, с предупреждением); `2` — хотя бы одна неполная/ошибочная выгрузка;
`1` — ошибка конфигурации или запуска. Каждая компания получает отдельную сводку.
`stats` хранит итоги и последние 20 запусков по boards, включая ошибки; повторный
успешный сбор тоже считается обновлением, даже если текст вакансии не изменился.

## Надёжность и модель данных

- Один общий HTTP-клиент выполняет последовательные GET-запросы с интервалом
  не менее 1 секунды по умолчанию. Тайм-аут — 20 секунд, максимум 3 попытки.
  Повторяются сетевые ошибки, тайм-ауты, `429` и `5xx`; задержка растёт экспоненциально
  с jitter, учитывает `Retry-After` и ограничена 60 секундами. Если сервер требует
  ждать дольше лимита, board завершается ошибкой до следующего запуска без раннего
  повторного запроса. Остальные `4xx`,
  редиректы и некорректный JSON возвращают ошибку без обхода защиты.
- Greenhouse запрашивается с `content=true`. Для полной выгрузки проверяются
  `jobs` и совпадение `meta.total`; неверные записи не уничтожают корректные.
  Lever использует `skip/limit` до пустой страницы, увеличивает offset на фактический
  размер ответа, выявляет повторяющиеся ID и ограничивает число страниц.
- Сбой одного board не прерывает другие. Из частичного ответа можно сохранить
  успешно разобранные вакансии, но выгрузка остаётся неполной.
- Уникальное ограничение БД — `(source, source_job_id)`. Повторный сбор обновляет
  запись, сохраняет внутренний UUID и `first_seen_at`, обновляет `last_seen_at`.
  Время хранится в UTC. Повторно найденная вакансия становится `active`.
- `source_board` дополнительно фиксирует board/регион, чтобы статус вакансий одной
  компании не зависел от результата другой. Неожиданное совпадение ID между boards
  одного источника фиксируется ошибкой и не перезаписывает чужую запись.
- Полный исходный объект вакансии хранится в `raw_data`; `description` содержит
  полный текст без HTML-разметки, включая секции списков и заключение Lever.
  При необходимости оригинальный HTML остаётся в `raw_data`.
- Отсутствующие данные остаются `null/unknown`. Неопубликованные зарплаты не
  извлекаются догадками. Структурная зарплата Lever сохраняется вместе с
  `salary_interval`, чтобы не смешивать часовые и годовые суммы. Неподдержанные
  варианты зарплат Greenhouse остаются в исходных данных. `seniority` — осторожная
  эвристика по явным маркерам названия; неоднозначные уровни остаются `null`.
- `updated_at` Greenhouse — только `source_updated_at`. `published_at` заполняется
  только при явно предоставленной дате публикации; Lever `createdAt` не используется.
  Дополнительные запросы к каждой карточке Greenhouse ради дат/зарплат пока не делаются.
- Кандидаты кроссплатформенных дублей — совпадения нормализованных компании,
  названия и непустой локации на разных платформах. `stats --duplicates` только
  сообщает о них, без удаления или слияния.

### Снятие с активности

По умолчанию отсутствие вакансии в следующем ответе **не меняет** её статус:
`mark_inactive_on_complete: false`. Это защищает историю при временно пустых boards
и изменениях выдачи. Если нужна автоматическая деактивация, включите её в sources YAML:

```yaml
mark_inactive_on_complete: true
allow_empty_deactivation: false
```

Только полный успешный результат без ошибок может сделать отсутствующие вакансии
этого board неактивными. Пустая выдача также требует отдельного
`allow_empty_deactivation: true`. Ошибки сети, валидации, пагинации и хранения не
снимают отсутствующие вакансии. API не обеспечивает транзакционный снимок: особенно
у Lever изменения между страницами могут дать незаметные пропуски. Для личного MVP
рекомендуется оставить деактивацию выключенной и запускать один сбор за раз.

## Периодический запуск

Приложение запускает один цикл и завершается: используйте внешний планировщик.
Установка задач планировщика автоматически не выполняется.

Linux cron, каждые 6 часов; замените `/absolute/path/JobRadar` реальным путём:

```cron
0 */6 * * * cd /absolute/path/JobRadar && /usr/bin/flock -n /absolute/path/JobRadar/data/collect.lock .venv/bin/python -m jobradar collect >> /absolute/path/JobRadar/data/collect.log 2>&1
```

Перед настройкой создайте `data/` либо выполните первый ручной сбор. `flock` нужен
для предотвращения пересечения запусков. На системах без него задайте аналогичное
ограничение в планировщике.

Windows Task Scheduler:

1. Создайте задачу с нужным интервалом, например каждые 6 часов.
2. Program: полный путь `JobRadar\.venv\Scripts\python.exe`.
3. Arguments: `-m jobradar collect`.
4. Start in: полный путь каталога `JobRadar`.
5. В настройках повторного запуска выберите **Do not start a new instance**.

Альтернативный ручной/планируемый вход — `scripts/collect.ps1`: он устанавливает
рабочий каталог и возвращает код завершения Python-команды. Для ценной SQLite-базы
предпочтителен локальный каталог без синхронизации OneDrive; путь можно изменить
через `JOBRADAR_DATABASE_URL`. Для резервной копии остановите сбор и используйте
SQLite backup либо сохраните БД после закрытия всех процессов.

## Тесты и качество

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m pytest --cov=jobradar --cov-report=term-missing
.\.venv\Scripts\python.exe -m ruff check .
.\.venv\Scripts\python.exe -m ruff format --check .
```

Обычные тесты не обращаются к интернету: JSON-фикстуры, `httpx.MockTransport`,
временные SQLite-базы. Покрыты оба API, пагинация, нормализация, сохранение полных
описаний, уникальность, обновление времён/ID, реактивация, безопасная деактивация,
частичные ответы, ошибки `429/5xx`, тайм-ауты, битые ответы, пустые boards,
география, фильтры, CLI и экспорт. Тесты с маркером `integration` по умолчанию пропускаются.

Необязательная реальная проверка (только публичные GET, требует интернет):

```powershell
$env:JOBRADAR_INTEGRATION = "1"
.\.venv\Scripts\python.exe -m pytest -m integration -q
Remove-Item Env:JOBRADAR_INTEGRATION
```

Linux/macOS: `JOBRADAR_INTEGRATION=1 .venv/bin/python -m pytest -m integration -q`.
Проверяются `cloudflare`, `torq`, `canarytechnologies`, `atmosera`, `lever` и официальный
`leverdemo`; тесты не пишут вакансии
в рабочую базу. Пустой корректный board допустим; схема и полнота проверяются.

## Структура и расширение

```text
jobradar/
  collectors/
    base.py               # интерфейс, HTTP, повторы, результат с признаком полноты
    greenhouse.py
    lever.py
    normalization.py
  models/job.py           # единый контракт Pydantic
  database/
    models.py             # SQLAlchemy, уникальность, UTC
    repository.py         # атомарные снимки и история запусков
  filters/rules.py        # объяснения совпадения и оценка географии
  services/
    collection.py         # изоляция boards, оркестрация
    export.py
    query.py              # выборка и кеш объяснений для веб-интерфейса
    configuration.py      # проверенное атомарное сохранение YAML
  web/
    app.py                # локальные HTTP-маршруты
    runner.py             # состояние фонового сбора
    launch.py
    static/               # HTML/CSS/JS без сборки
  config.py
  cli.py                  # только пользовательский вход
config/
  sources.example.yaml
  profiles.example.yaml
scripts/collect.ps1
Start-JobRadar.cmd
tests/
  fixtures/
pyproject.toml
requirements-lock.txt
.env.example
```

Сервисы не зависят от Typer: CLI и локальный FastAPI-интерфейс используют общую
логику сбора/фильтров/экспорта. Веб-слой находится в `jobradar/web`, статические
HTML/CSS/JS включаются в пакет, сборка Node.js не требуется. Для нового источника
реализуйте `Collector.collect(SourceConfig)` с
результатом `CollectorResult(jobs, complete, errors)`, нормализацией в `Job` и
расширьте конфигурацию/реестр адаптеров. Не привязывайте поисковые предпочтения
к сборщику.

SQLAlchemy использует переносимые типы и транзакции. Для PostgreSQL понадобится
установить соответствующий драйвер, поменять URL и перенести данные; реальный
PostgreSQL в MVP не тестировался. `create_all` создаёт исходную схему, но не
мигрирует существующую: перед развитием модели следует добавить Alembic.

Текущие ограничения: только явно настроенные работодатели, нет глобального поиска
по платформам; только опубликованные публичные данные; нет полного словаря стран,
морфологии и семантического анализа; поиск выполняется в памяти и рассчитан на
личную базу, а не миллионы вакансий. Задержки и форматы внешних API могут меняться.
CAPTCHA, авторизация и антибот-защита не обходятся. [Документация Greenhouse](https://docs.greenhouse.io/job-board.html),
[документация Lever](https://github.com/lever/postings-api).

Следующие полезные шаги: подобрать проверенный список работодателей под профиль,
расширить фикстуры географии реальными формулировками, добавить миграции и историю
изменений вакансий, затем уведомления о новых совпадениях. AI-анализ,
управление откликами и подготовка резюме остаются отдельными этапами.
